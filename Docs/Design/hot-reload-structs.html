Hot reloading structs in eacp

Status: phase 1 implemented on jp/hot-reload-library. Deviations are noted where they apply (5.2, 6.1, 6.2, 7.3, 8, 10).

1. Requirements

  1. Off means off. With hot reload disabled, the build is an ordinary static binary. No dylib, no module target, no indirection in user code, no extra bytes in user structs.
  2. Users write only the reload behaviour. A user marks what reloads and, if needed, writes what happens after a reload. They do not write plumbing: no factories, no interfaces, no registration, no symbol names.
  3. Free functions and structs are both reloadable.

2. What exists today

A hot build (eacp_add_hot_reload(... HOT_RELOAD ON)) compiles the chosen source files twice: into the app as normal, and into a module (a .so on macOS). The app, every static library in its link closure and the module are compiled with default symbol visibility, the app is linked with -export_dynamic, and the module is linked with -undefined,dynamic_lookup. So the module can call anything in the app, and the app can look up anything in the module by symbol name.

A HotReloadLoop watches the source directory, runs cmake --build --target <module> on a change, copies the result to a fresh path and dlopens it. The previous image is unmapped one event-loop turn later.

Only free functions reload. The user holds a Plugins::Reloadable<&fn> handle and calls through it. On each reload the handle asks the loader for the symbol name of the app's own copy of fn (dladdr), looks that name up in the fresh image (dlsym), and stores the pointer. Nothing spells a mangled name.

3. The one fact that decides the design

C++ binds a call to a non-virtual function at link time. If the app contains cow.makeParts(), that call goes to the app's CowModel::makeParts forever. Loading new code somewhere else changes nothing about that call site. The only calls the language late-binds are virtual calls and calls through function pointers.

Consequences:

  • A struct's methods can only be reloaded if they are virtual.
  • "Reloading a struct" means making the virtual calls on existing instances land in the new image. Nothing else is possible without rewriting machine code in the running process.
  • No reflection on method names is needed. The compiler has already built the method table: the vtable.

4. Two candidate mechanisms for structs

4.1 Recreate through a factory

The module exports a factory. The app holds instances through a base-class pointer and never names the concrete type. On reload the app destroys each instance and asks the fresh image's factory for a new one, optionally handing the old instance over so state can be copied. This is what Apps/GPU/HotReload does by hand today.

4.2 Swap the vtable pointer in place

Instances stay where they are. On reload, for each live instance: read its vtable pointer, ask the loader which symbol it points into (for example _ZTV8CowModel + 16), find the same symbol in the fresh image, and write the new address into the instance. Virtual calls on that instance now run the new code. Then call a user hook, onReload(), so the instance can rebuild anything it derived from the old code.

Decision: 4.2. It is the only one that meets requirement 1 (zero cost when off) and requirement 2 (no plumbing). The price is the layout restriction and the ABI dependence, both stated in section 6.

5. Proposed user-facing API

5.1 Structs

struct CowModel : Plugins::Reloadable<CowModel>
{
    EACP_RELOADABLE Vector<CowPart> makeParts() const;
    EACP_RELOADABLE JumpPhysics getJumpPhysics() const;

    // Optional. Called on every live instance after each reload.
    EACP_RELOADABLE void onReload();
};

CowModel cow;        // a member, a local, an element of a Vector: anywhere
cow.makeParts();     // an ordinary call

Hot reload off: EACP_RELOADABLE expands to nothing and Plugins::Reloadable<T> is an empty class with no members and no virtual functions. CowModel has no vtable pointer and no registration. onReload() is never called.

Hot reload on: EACP_RELOADABLE expands to virtual. Plugins::Reloadable<T> registers this in its default, copy and move constructors and removes it in its destructor. The registry is a process-wide list in eacp-core of (pointer to the complete T, pointer to a thunk that calls onReload() on it). The thunk is a lambda instantiated per T in the base's constructor, so eacp-core never names a user type.

Plugins::Reloadable<T> has no virtual functions of its own, on or off. Section 7 explains why: a polymorphic base adds a second vtable pointer to any struct that also derives from another polymorphic class, and the swap handles exactly one.

5.2 Free functions

Unchanged from today, with one improvement:

Implemented as Plugins::ReloadableFunction<&fn>, so the name does not collide with the struct base.

Plugins::ReloadableFunction<&makeCowParts> makeLiveCowParts {cowModel};
makeLiveCowParts();

When hot reload is off, operator() calls makeCowParts directly (if constexpr) and the handle holds no data. A user who does not want the handle at the call site puts the function on a struct.

A free function cannot be made reloadable without a handle at the call site. A direct call is bound at link time (section 3). Any macro that hid this would have to generate a function pointer and a wrapper, which is the same handle with worse error messages.

6. Mechanism in detail

6.1 The swap

  1. The loop loads the fresh image.
  2. For each registered instance, read the vtable pointer at offset 0 of the complete object.
  3. dladdr on that pointer gives the nearest preceding exported symbol and the offset from it, for example _ZTV8CowModel and 16. This names the dynamic type of the instance, so derived classes need no special handling. (Today's getExportedSymbolName requires an exact match; this needs a second form that returns symbol and offset.)
  4. dlsym that symbol in the fresh image. If it is absent, the type was not compiled into the module: abort with the type named.
  5. Run the size check if one is configured (6.2). If it fails, refuse the whole reload and keep the previous generation.
  6. Write new vtable address + offset into the instance.
  7. After all instances are swapped, call onReload() on each, through the new vtable, so the new code's onReload runs.

Invalid reloads abort. Policy: when the swap meets an inconsistency it cannot make safe (a vtable missing from the fresh image, a second vtable pointer, a size mismatch if a check exists, a reload with a header changed since launch), it prints one line on stderr naming the type or file and what to do, and calls std::abort(). Build and load failures stay soft and keep the previous generation.

Implemented: all instances are resolved first, so an abort happens before any pointer is written. The vptr is checked to lie in a _ZTV symbol; anything else aborts as "no exported vtable".

The old image is unmapped one loop turn later, as today. Every registered instance now points into the new image, so nothing references the old one.

6.2 Size check

The swap is only safe if the module's sizeof(T) and member layout equal the app's. A check needs the module's sizeof(T), read from the fresh image before anything is swapped. The obvious way is a hidden virtual, virtual std::size_t getReloadableSize() const { return sizeof(T); }, whose slot the loop reads from the fresh vtable and calls. The function only returns a constant, so calling it with a host instance as this is safe.

Where that virtual is declared is a real tradeoff:

OptionUser codeConsequence
A. Declare it in Reloadable<T> Nothing extra. The base becomes polymorphic. A struct that also derives from another polymorphic class (struct DemoView : GPUView, Reloadable<DemoView>) then has two vtable pointers, which the phase 1 swap cannot handle (section 7). This rules out the view example. Rejected for phase 1.
B. Declare it in T through a macro in the struct body, EACP_RELOADABLE_STRUCT(CowModel); One extra line inside every reloadable struct. A virtual declared in the derived class goes into the primary vtable, so the object keeps one vtable pointer whatever its first base is. The size check works. Costs one line of what requirement 2 calls plumbing.
C. No size check in phase 1 Nothing extra. A member added or removed while running corrupts memory with no diagnosis. The loop can still refuse to reload after any header change under the watched directory, which catches the realistic way a layout changes (editing the struct's header), but not a struct defined in a .cpp.

Implemented: C. The loop hashes every header under the watched directory at launch; a change event for a header whose contents differ does not build, and a reload while any differs aborts. Undoing the edit clears it.

Proposed: C for phase 1, with the header-change refusal. B is the fallback if that proves too thin in practice. A returns in phase 2 once multiple vtable pointers are handled (section 7.4).

Any size check is partial. It catches a member added or removed. It does not catch a member changed to another type of the same size, or two members reordered. Those corrupt memory silently. The rule for users is: edit function bodies in .cpp files; a change to a struct definition needs a restart.

6.3 Where the vtable lives

For the swap to work, the fresh image must contain the type's vtable. The compiler emits a class's vtable in the translation unit that defines its key function (the first non-inline, non-pure virtual function declared in the class). If that function is defined in a file in the module's SOURCES, the vtable is in the module. If every virtual is inline, the vtable is emitted in every TU that needs it, including the module's. Either way the module has it. If the key function is defined in a file that is not in SOURCES, the type cannot be reloaded, and step 4 above reports it.

6.4 Methods not in the module

A virtual method defined in a file outside SOURCES still has a slot in the module's vtable, and that slot points at the app's copy via dynamic_lookup. The call works and runs the old code. The same holds for non-virtual helpers called from reloaded virtuals: a helper defined in a module source runs the new code, one defined elsewhere runs the app's copy. Nothing breaks; the user just reloads less than they might expect. This replaces the question "what if methods are spread over several TUs". The answer is: it works, file by file.

6.5 Why the reloaded code is compiled twice, and what that costs

In a hot build the reloaded sources are compiled into the app and, separately, into the module. The process holds two definitions of every function and type in those files: the app's, used until the first reload, and the module's, used after. This is deliberate, and it is the same situation as any plugin that statically links a library the host also links. It is not the ODR as the standard defines it (one program, one definition) because each image is linked separately, but the practical hazards of two definitions are real and are listed below.

Why not compile the sources only into the module and have the app use the module's symbols? Because of how the app's call sites get bound. If the app does not contain makeCowParts, every reference to it in the app is an undefined symbol that the dynamic linker resolves once, at launch, to the first image that defines it. That binding is stored in the app's GOT and lazy-pointer tables. Loading a second image later changes nothing: the app's references still point into the first image. Two ways out:

ApproachWhat it needsWhat it would giveWhy not now
Rebind the app's GOT on every reload Parse the app's Mach-O (bind opcodes or chained fixups) and ELF (.rela.plt, .rela.dyn) relocation tables, find every slot bound to a module symbol, mprotect the page, write the new address. fishhook does this on macOS and has needed rework for each dyld change (chained fixups, __DATA_CONST). Every direct call from the app into reloaded code is redirected, with no handle at the call site. Free functions reload without Reloadable<&fn>. Non-virtual methods reload too, because a call to a function in another image already goes through the GOT. New instances pick up the new vtable automatically. This is the only route that removes the handle for free functions and the devirtualisation risk of section 10. It is a large amount of platform-specific, fragile code, different on macOS and Linux, and it breaks when the OS changes its loader. Existing instances still need the vtable swap of section 6.1, so it adds to the design rather than replacing it. Worth a spike after phase 1 proves the rest.
Reach the module only through handles and factories Nothing new. One definition per process at a time. The app can no longer construct a reloadable struct itself: the constructor needs the type's vtable address, which would be in the module only. Every instance must come from a module factory and be held through a pointer. That is design 4.1, which fails requirements 1 and 2.

What the two copies buy, as the design stands:

  • The app runs with no module loaded. Generation 0 is the app's own code. A module that fails to build or load leaves a working program.
  • Hot reload off is the same arrangement with the module target removed. There is no separate code path for the static build to drift from.
  • Symbol discovery without spelling names: dladdr on the app's copy of a function or vtable gives the name to look up in the module.
  • The app can construct reloadable structs by value, because their vtables exist in the app.

What the two copies cost. These are the real "ODR land" hazards and each one is a rule for users of the mechanism:

HazardDetailRule or mitigation
Globals and function-local statics exist twice The app's copy and the module's copy of a static in a reloaded .cpp are different variables. After a reload the module's starts from its initialiser. Documented already. Reloaded files should not keep state in statics; keep it in the struct, which survives the swap.
RTTI across the boundary typeid, dynamic_cast and exception catch matching compare type_info objects. The app's _ZTI8CowModel and the module's are different objects. libc++ on Apple compares by address for types it considers unique, so a dynamic_cast<CowModel*> in app code on an instance whose vtable now points into the module can fail, and an exception of a reloaded type thrown by module code may not be caught by an app-side catch of that type. Do not dynamic_cast to, or throw, types defined in reloaded files. Both are rare in the code this is for. Can be verified with a test case before shipping.
Layout drift between copies The app's copy was compiled from the header as it was at launch; the module's from the header as it is now. Section 6.2: edit bodies, not definitions; refuse to reload after a header change.

Module references to its own symbols With a two-level namespace (macOS) the module's internal calls to functions it defines bind to itself at link time. With -undefined,dynamic_lookup only its undefined symbols are resolved against the app. On Linux the equivalent is the default for a shared object unless -Bsymbolic is absent and the symbol is preemptible; the module should be linked with -Bsymbolic so its own definitions win. 7. Multiple inheritance in detail

Implemented differently from 7.3: the scan runs at each swap, not at registration (the derived vptr is not yet written while the base constructor runs), and needs no symbol size: a word at a non-zero offset is a second vtable pointer when dladdr names the same _ZTV symbol for it. It aborts with the type named.

7.1 How the object is laid out

Under the Itanium C++ ABI, a class with virtual functions has one vtable pointer per polymorphic base subobject, plus one of its own if it introduces virtual functions and has no polymorphic base to share with. The first polymorphic non-virtual base is the primary base: it sits at offset 0 and the derived class shares its vtable pointer. Every other polymorphic base is a secondary base at a non-zero offset with its own vtable pointer.

struct A { virtual void a(); int x; };
struct B { virtual void b(); int y; };
struct D : A, B { void a() override; void b() override; int z; };

D in memory (64-bit):
  offset  0   vptr  -> _ZTV1D + 16            (primary: D-in-A vtable)
  offset  8   int x
  offset 16   vptr  -> _ZTV1D + 16 + N        (secondary: B-in-D vtable)
  offset 24   int y
  offset 28   int z

Both pointers point into the same symbol, _ZTV1D, the vtable group for D: the primary vtable followed by one secondary vtable per secondary base. The compiler emits the whole group as one object with one symbol.

A B* that refers to a D holds the address of offset 16, not offset 0. A virtual call through it reads the secondary vtable pointer.

7.2 What the phase 1 swap does to such an object

Phase 1 rewrites the pointer at offset 0 only. After a reload:

  • Calls through a D* or A* use the new image. Correct.
  • Calls through a B* read offset 16, which still points into the old image. For one loop turn that runs stale code. After the old image is unmapped, it is a jump into unmapped memory: a crash, at the first such call, with no connection visible to the edit that caused it.

This is why Reloadable<T> must not be polymorphic in phase 1 (section 6.2, option A). With the view example, struct DemoView : GPUView, Reloadable<DemoView>, GPUView is the primary base and a polymorphic Reloadable would be a secondary base with its own vtable pointer. eacp holds views as View*, which here is the primary, so the app's calls would work, but onReload() dispatched through the secondary pointer would not, and the unmapped image would still be referenced.

7.3 Phase 1 rule and how it is enforced

Rule: a reloadable struct may have at most one polymorphic base, and it must be the first base listed. Reloadable<T> itself does not count because it has no virtual functions.

Enforcement options, in order of strength:

  • Documentation only. The failure mode is a crash on the first call through a secondary base after a reload, which is hard to diagnose. Not acceptable on its own.
  • Compile time. C++ has no way to enumerate a type's bases or count its vtable pointers, so the general case cannot be asserted. static_assert(!std::is_final_v<T>) and static_assert(std::is_polymorphic_v<T>) are possible but do not catch multiple inheritance.
  • At registration, by scanning the object. When an instance registers, the base knows sizeof(T) and the complete-object pointer. Read every pointer-aligned word in [this, this + sizeof(T)) and count those whose value lies inside the address range of the vtable group the first word points into. More than one means more than one vtable pointer: refuse the type at startup with a message naming it. This needs the size of the vtable group symbol, which dladdr does not return. On macOS it is in the Mach-O symbol table, which DynamicLibrary::getFunctionNames already parses; on Linux it is st_size in the ELF dynamic symbol table (dl_iterate_phdr plus the .dynsym walk). Proposed for phase 1, since it turns a crash into an error at startup.

The scan has a false positive if a data member holds a pointer into the vtable group. No ordinary member does; a function pointer points at code, not at a vtable. A false positive produces a clear refusal, not a crash.

7.4 Phase 2: rewrite every vtable pointer

The same scan that detects multiple vtable pointers can fix them. Every word in the object that points into the old vtable group is a vtable pointer at some offset into the group; add the same offset to the new group's address and write it back. This handles multiple inheritance and, because objects use the same vtable group at runtime (construction vtables are only used while constructors run), virtual inheritance too.

What it does not handle: a member object that is itself polymorphic but of a type not compiled into the module. Its vtable pointer points into a different symbol, not the group being swapped, so the scan skips it. That is correct, because that type's code did not change.

With phase 2 in place, Reloadable<T> may become polymorphic again and the size check of section 6.2 option A becomes available with no extra user code. The ordering rule in 7.3 also goes away.

Phase 2 is not proposed for the first implementation because phase 1 covers every current use (a plain struct, or a struct with one eacp base such as GPUView) and the symbol-size lookup is new platform code on two platforms.

8. Build system changes

  1. EACP_HOT_RELOAD becomes a build-wide compile definition. Today it is PRIVATE to the app target. EACP_RELOADABLE adds a vtable pointer to a struct, so every translation unit that includes the struct's header must see the same value, or the program has two layouts for one type (an ODR violation that will crash). When any eacp_add_hot_reload in the build is ON, the definition is added to every compiled target in the build. The docs already say a hot build is a property of the whole build directory because of the visibility change, so this adds no new restriction.
  2. Implemented as a walk of every directory's BUILDSYSTEM_TARGETS at the end of the configure, since a directory-scope definition only reaches targets created after it. The examples no longer force HOT_RELOAD ON, or a static configure would be hot.
  3. The per-app definitions (module path, build directory, target name, source directory) stay on the app, as today.
  4. Nothing else changes in CMake. The LIBRARY form on the branch already lets the struct's .cpp live in a static library and be compiled into the module.

10. Risk that needs a test before relying on this

Devirtualisation. When the compiler can prove an object's dynamic type, it may replace a virtual call with a direct call. For CowModel cow; cow.makeParts(); the compiler knows the object is exactly a CowModel, and at optimisation levels above -O0 it is permitted to call CowModel::makeParts directly. That call would bypass the swapped vtable and run the old code, silently.

At -O0 compilers do not devirtualise, and hot reload builds are Debug builds, so the common case is safe. A Release build with hot reload on is the case at risk.

Measured (Apple clang, arm64): the premise above is wrong. Clang emits a direct call for object.method() when object names a local or a by-value member, even at -O0; through a pointer or reference it calls through the vtable at -O0 and -O2 (a local reference variable is enough). The registry's thunk calls through a pointer, so onReload and every call eacp makes through a base pointer reload in Debug and Release (the example reloaded in a Release hot build). The fallback in use: call reloadable methods through a reference or pointer, documented; Cows does const auto& cowModel = scene.cowModel;. gcc not tested.

Before the design is accepted, build a small test: a struct with an EACP_RELOADABLE method, held by value as a member and as a local, called at -O2 with clang and gcc, and check the generated code calls through the vtable. If it does not, the fallback is for the hot build to compile the app's sources at -O0, or for Reloadable<T> to route calls through a non-inlinable accessor, which would weaken requirement 2.

11. Effect on the examples and on Cows

  • Apps/GPU/HotReload and HotReloadLibrary: the view becomes struct DemoView : GPUView, Plugins::Reloadable<DemoView> with external linkage, GPUView first so it is the primary base (section 7.3). onReload() recompiles its shader. The factory, the ViewABI.h header, and the destroy-and-recreate code in Main.cpp are deleted. GPUView's virtuals are already virtual, so no EACP_RELOADABLE is needed there.
  • Cows: makeCowParts and getJumpPhysics become methods of a CowModel struct as in 5.1. The scene holds a CowModel by value. The two function handles in CowsApp.h are deleted. The app still needs one callback from the loop to tell the scene to pull the parts again, because CowModel::onReload() has no reference to the scene. That callback is reload behaviour, not plumbing.

12. Open questions

  1. Should onReload() be mandatory (static_assert) or optional (if constexpr (requires ...))? Optional is proposed: the view example has nothing to do in it.
  2. Should the loop refuse to reload after any header change under the watched directory, or only warn? Refusing is safer and is proposed.
  3. Size check: ship phase 1 with none (option C) or with the body macro (option B)? None is proposed; see 6.2.
  4. Should GOT rebinding (6.5) be spiked after phase 1? It is the only route to reloading free functions and non-virtual methods with no handle.
  5. Keep Reloadable<&fn> for free functions, or tell users to use structs only? Keeping it is proposed; it is small and already works.
